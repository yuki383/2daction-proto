# Development Plan — 小さく実装し、理解して進む

> 状態: 初稿（v0.1） / 更新日: 2026-10-15  
> フェーズ分割は**作業計画案**。ゲームデザイン自体を固定するものではない。各フェーズは完成・レビューしてから次へ進む。

## 1. 開発の優先順位

1. **プレイヤーの操作感**を成立させる。
2. **単発攻撃と回避の駆け引き**を成立させる。
3. **敵のモーション・スーパーアーマー**で通常戦闘を成立させる。
4. **ボス1体との戦闘**を完成させる。
5. **能力解放・探索・アート**を必要最小限から追加する。

ゲーム全体の方向性は [`game-vision.md`](game-vision.md) に残し、現在の実装範囲は [`prototype-spec.md`](prototype-spec.md) で明示する。

## 2. フェーズ案

| Phase | 主な作業 | 理解・検証の焦点 | 完了の目安 |
| --- | --- | --- | --- |
| **0: 設計資料と土台** | 仕様ドキュメント、Codex運用ルール、Godotプロジェクト作成 | シーン・ノード、Godotプロジェクト構成 | Codexが設計資料を参照できる |
| **1: 基本移動（今回）** | `A/D`移動、`Space`ジャンプ、重力と床 | 物理更新、Input Map、`CharacterBody2D` | 小さなテストステージで操作できる |
| **2: 操作感と足場** | 可変ジャンプ、加減速、空中制御、入力補助、すり抜け床 | 速度・重力、入力タイミング、床判定 | 意図した高さ・移動方向に気持ちよく動ける |
| **3: 地上ダッシュ** | ダッシュ移動、短い無敵時間、再使用条件、デバッグ表示 | 時間窓、状態と衝突判定 | ダッシュと無敵の関係を検証できる |
| **4: 通常攻撃** | `W`単発攻撃、地上／空中攻撃、硬直、ダッシュキャンセル、先行入力 | 攻撃の状態遷移、判定と入力バッファ | 攻撃と回避のリスクを試せる |
| **5: 雑魚敵の戦闘** | 小型の敵、複数体配置、モーション依存のスーパーアーマーを持つ敵 | AI、ヒットリアクションと怯み、1対多 | 攻撃連打だけが最適解にならない |
| **6: ボスの基本戦闘** | ボス1体、少数の予兆と攻撃、回避・反撃 | 予兆→判定→硬直、難易度調整 | ボスを観察して倒す手応えがある |
| **7: ボスギミック** | 紋章等の時間差攻撃、限定的なブレイク、別解の検証 | ギミックの法則、視認性、無敵との関係 | 失敗・学習・再挑戦が成立する |
| **8: 小さなゲーム体験** | ボス撃破で能力解放、空中ダッシュ、短い探索ルート | 成長と探索のつながり | 新能力を使う短いプレイループが完成 |
| **9: 演出・公開準備** | ドット絵、アニメーション、効果音、UI、難易度調整 | ヒットの手応え、視認性、制作パイプライン | 最小スコープの完成版として遊べる |

**重要:** 上表は段階の全体像であり、**いま実装するのはPhase 1のみ**。Phase 2以降の詳細をCodexが独断で実装しないこと。

## 3. 各フェーズの実施サイクル

### ① 仕様を小さく定義する

- このチャットでゲームデザインの目的と、今回だけの実装範囲を整理する。
- 設計の合意・仮案・未決定事項を分ける。
- 必要なら`prototype-spec.md`を次フェーズ向けに更新する。

### ② Codexに実装を任せる

- `AGENTS.md`と対象ドキュメントを読ませる。
- 1回の依頼では変更対象と完成条件を絞る。
- 未指定機能の先行実装、過剰な汎用化、大量の依存追加を避ける。

### ③ コードを理解する

- シーンツリー・各スクリプトの責務を確認する。
- 新しく登場したGodot固有のAPIを説明できるようにする。
- Web開発での既存知識と何が同じで何が異なるかを理解する。

### ④ 実際にプレイして検証する

- Codexが実装できたことと、プレイヤーが楽しいと感じることは区別する。
- 特に移動速度・ジャンプ・攻撃硬直・無敵時間は、プレイ結果を見て調整する。
- テスト不能な項目は完了扱いにしない。

### ⑤ 決定を残す

- 重要な仕様変更と理由を`decisions.md`に記録する。
- 目標と実装のズレがあれば`game-design.md`や`prototype-spec.md`を更新する。
- 調整途中の細かな数値は、資料に無理に固定せずInspector等で管理する。

## 4. マイルストーン

### M1: 動くプレイヤー

左右移動とジャンプができ、物理更新とノードの役割を説明できる。**最初に目指す成果。**

### M2: 回避と攻撃の基本ループ

ダッシュの短い無敵時間、単発攻撃、キャンセルできない硬直、先行入力が動作し、単純な敵相手に戦闘の感触を検証できる。

### M3: ボス1体との完成した戦闘

少数の攻撃とギミックで、観察→回避→反撃→学習の面白さが成立する。ここを**最初の大きなゲームプレイ上の到達点**にする。

### M4: 能力解放を含む小さな遊び

ボス撃破で能力を獲得し、探索・次の戦闘で使う短い体験を作る。最終規模はこの段階の制作負荷を見て確定する。

## 5. やらないこと・変更してよいこと

- 最初から「メトロイドヴァニア完全版」の構造を作らない。
- ドット絵・背景・物語制作を、基本戦闘が動く前の必須条件にしない。
- 初期のボス数・部屋数・プレイ時間は確定しない。必要なら縮小する。
- 最初に選んだ実装方針が非効率なら見直す。ただしゲームデザイン上の変更は明示して合意を取る。

## 6. 実装を通じて学びたいGodotの概念

| 学習対象 | 主に触れるフェーズ |
| --- | --- |
| シーン・ノード・シーンのインスタンス化 | 0〜1 |
| `_physics_process`、`delta`、Input Map | 1 |
| `CharacterBody2D`、速度と衝突判定 | 1〜2 |
| すり抜け床、接地判定 | 2 |
| 時間窓と状態管理、デバッグ表示 | 3〜4 |
| `Area2D`等を使った攻撃判定 | 4〜5 |
| 敵AI、状態遷移、スーパーアーマー | 5〜6 |
| タイムライン・アニメーションによる予兆の表現 | 6〜7 |
| 能力解放とシーン間の進行 | 8 |
| スプライトシート・ピクセルアートの表示 | 9 |

必要な概念をその時点で学ぶ。将来のための大規模な設計を最初から作らない。
